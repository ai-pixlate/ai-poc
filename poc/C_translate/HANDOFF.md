## 0. 한 줄 요약

**하네스는 완성돼 잘 돌아가고 실측 데이터도 충분히 쌓였다. 깨진 것은 판정 방식이다.**
후보 4종 번역·비교는 끝났으나 **judge 절대 점수가 모델을 가르지 못해** 채택 결정을 못 내렸다.

## 1. 지금까지 확정된 것 — 그대로 가져갈 것

| 항목 | 값 |
|---|---|
| 목표 언어 | **한국어 → 영어** |
| 평가 데이터 | **합성 데이터** (실제 OCR 출력 아님) |
| 후보 4종 | `claude-opus-5` / `gpt-5.5` / `gemini-3.1-pro-preview` / `qwen3.8-max` |
| 참고 측정 | `qwen-mt-plus` (번역 전용, 후보 아님) |
| judge 모델 | `claude-opus-5`, 5점 척도 |

**합성 데이터를 쓰는 이유**: 1차에는 B(OCR) 출력을 썼는데 88건 중 17건에 문맥 추정이 필요해 **OCR 오류와 번역 품질이 섞였다**. C는 번역 능력을 재는 과업이므로 원문이 정확하다는 가정으로 바꿨다.

**함정 6유형 설계 — 이번 검증 최대 성과. 반드시 승계할 것**

| 유형 | 내용 | 기대 동작 |
|---|---|---|
| A | 주장 / 부인 문맥에 같은 금지어 | 주장은 치환, **부인은 유지** |
| B | 부분 일치 (`재생` vs `재생력`) | 치환 |
| C | 제품명 안의 금지어 | **유지** (프롬프트의 제품명 규칙과 충돌) |
| D | 인용문 안의 금지어 | **유지** (제3자 발화 왜곡 방지) |
| E | 한 문장에 금지어 2~3개 | 치환 |
| F | 조사·어미 결합 | 치환 |

정의 위치: `synthetic_source.py` 의 `TRAPS` 딕셔너리.

## 2. 깨진 것 — 재설계 대상

### ① judge 절대 점수가 변별을 못 한다 (가장 큰 문제)

| 후보 수 | 전체 평균 격차 |
|---|---|
| 2종 | 0.05 |
| 3종 | 0.05 |
| **4종** | **0.05** |

후보를 늘려도 격차가 그대로다. 4종 모두 4.72~4.77에 몰린다.

### ② 평가 축 4개 중 일부가 기능하지 않는다

| 축 | 5점 만점 비율 |
|---|---|
| `length` | **96.1%** ← 사실상 측정 안 됨 |
| `regulation` | 79.7% |
| `terminology` | 78.9% |
| `quality` | 52.3% |

### ③ 통과선을 정할 수 없다

4.0에 그으면 4종 전부 통과, 4.8이면 4종 전부 미달. 어디에 그어도 같이 움직인다. **보류 상태.**

### ④ 반대로 — 함정 정답률은 변별이 된다

기대 동작 대비 정오로 집계하면(치환 여부가 아님):

| 대상 | 정답률 |
|---|---|
| `gpt-5.5` | **76%** |
| `qwen3.8-max` | **76%** |
| `qwen-mt-plus` *(참고)* | 76% |
| `claude-opus-5` | 72% |
| `gemini-3.1-pro-preview` | 69% |

**폭 7%p** vs judge 절대 점수 폭 1%. **재설계는 이 축을 중심에 놓는 것이 유력하다.**

## 4. 코드 자산 — 재작성 불필요

`poc/C_translate/` 14개 파일 / 1,765줄. **4종 어댑터·캐싱·비용추정 전부 동작 검증됨.**

| 파일 | 역할 |
|---|---|
| `config.py` | 모델 레지스트리(ID·단가·엔드포인트), 확정/미확정 설정 |
| `prompts.py` | 번역·judge 프롬프트. 4종에 **같은 문안**을 쓴다 |
| `synthetic_source.py` | 합성 평가셋 원본 + `TRAPS` 함정 정의 |
| `build_evalset_synthetic.py` | 원본 → `evalset.json` |
| `build_evalset.py` | (구) B OCR 출력 → 평가셋. 현재 미사용 |
| `regulation_table_TEST.py` | **테스트용 더미 용어집 15항목.** 실제 규제 자료 아님 |
| `run.py` | 번역 실행. 4벤더 어댑터·캐싱·dry-run |
| `run_mt.py` | `qwen-mt-plus` 참고 측정 (별도 API 형태) |
| `judge.py` | LLM-as-judge 채점·집계 |
| `compare.py` | 비교표 생성 (`summary.md`) |
| `estimate_cost.py` | 호출 전 비용 추정 |
| `emit_session.py` · `session_translations*.py` | 세션 예비 실행 기록 |

**안전장치 (유지할 것)**

- `run.py` / `judge.py` / `run_mt.py` 모두 **기본 dry-run**, `--execute` 명시 필요
- API 응답 캐싱 → 재실행 무료
- **프롬프트 지문(SHA-256) 캐시** — 용어집이나 프롬프트가 바뀌면 자동 무효화
- judge 캐시 키에 **채점자·척도** 포함 (`judge_{모델}_s{척도}_{대상}`)
- DashScope 레이트 리밋 지수 백오프

## 5. 블로커 — 재계획으로 풀리지 않음

### ① 규제 매핑 테이블 실제 스펙 미합의 (선행 조건)

현재 쓰는 `regulation_table_TEST.py`는 **내가 만든 가짜**다. 법령 확인을 거치지 않았다.

**지금 변별의 대부분이 규제 함정에서 나오고 있으므로, 가짜 표로 고른 모델이 진짜 표에서도 1등이라는 보장이 없다.** 재계획 문서 첫머리에 **"이 검증의 결론은 실제 규제 표 확보 전까지 잠정"**이라고 명시할 것.

담당: 데이터 담당과 합의 (PoC 문서 2.3 선행 조건)

### ② 규제 표 스펙에 반드시 들어가야 할 것

후보 4종이 **치환은 잘하는데 치환 억제를 못 한다.** 공통 실패 3유형이 전부 "치환하면 안 되는 자리"였다.

- 부인·고지 문맥 (`~보장하지 않습니다`, `~입증된 바 없습니다`)
- 인용부호 안의 제3자 발화
- 제품명

### ③ 프롬프트 규칙 우선순위 미정

제품명 유지 vs 규제 치환이 충돌할 때 **GPT·Qwen은 제품명을, Claude·Gemini는 규제 표를 우선**했다(2:2). 정답을 정해 프롬프트에 못박아야 모델 간 편차가 사라진다.

## 6. 새 세션에서 주의할 것

**① v1 / v2 데이터를 섞지 말 것**

평가셋이 두 번 바뀌었다. 문서에 남은 수치 중 **v1 기준인 것은 현재와 비교 불가**다.

| | v1 | v2 (현재) |
|---|---|---|
| 세그먼트 | 64 | **89** |
| 용어집 | 8항목 | **15항목** |
| judge 실행 | ✅ 4종 | ❌ **미실행** |

**judge v2는 한 번도 안 돌렸다.** 문서의 judge 점수 4.72~4.77은 전부 v1 기준이다.

**② 참고 측정을 후보와 같은 표에 놓지 말 것**

`qwen-mt-plus`는 시스템 프롬프트·JSON 출력·문맥 전달이 모두 불가해 조건이 다르다. 실제로 이번에 같은 표에 넣었다가 **미실행을 오답으로 세어 정답률을 52%로 오독**한 사고가 있었다(실제 76%).

**③ 유료 호출 전 반드시 비용 보고 (CLAUDE.md 규칙)**

새 모델은 **1건만 먼저 돌려 출력 길이를 실측한 뒤** 전체를 추정할 것. `qwen3.8-max`에서 추정이 543% 빗나갔다 — 출력의 91%가 추론 토큰이었다. 문자수 근사는 모델마다 출력 길이가 비슷하다는 가정에 서 있어 위험하다.

**④ 등급·점수를 임의로 채우지 말 것** (CLAUDE.md 규칙)

**⑤ API 키는 `.env`에 4종 모두 있음** — `OPENAI` / `ANTHROPIC` / `GOOGLE` / `DASHSCOPE`. 코드에 하드코딩 금지.

**⑥ 환경**: `.venv` (paddle·openai·anthropic 공존). E1용 `.venv-e1`은 별개.

## 7. 재설계 시 결정할 4가지

| # | 항목 | 현 상태 |
|---|---|---|
| 1 | **판정 방식** | judge 절대 점수 폐기 후 무엇을 쓸 것인가. 함정 정답률 / 쌍대 비교(A/B) / 실측 항목 중심 |
| 2 | **평가 축** | 현 4축 중 `length`는 96% 만점으로 기능 없음. 축 재정의 필요 |
| 3 | **통과선** | 절대 점수를 안 쓰면 개념 자체가 바뀜 |
| 4 | **표본 규모·난이도** | 89건이 적절한지. 함정 29건이 변별의 대부분을 만들고 있음 |

**쌍대 비교(A/B)** 가 유력한 후보다 — "두 번역 중 어느 쪽이 나은가"를 묻는 방식으로, 절대 점수보다 미세한 차이에 민감하고 천장 효과가 없다. 4종이면 6쌍 × 89건. 아직 시도하지 않았다.
